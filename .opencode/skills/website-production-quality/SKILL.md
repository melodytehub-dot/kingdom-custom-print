# Universal Website Production Quality

## Mission

Treat every website as a real product meant for its own audience—not an AI demo, portfolio of implementation steps, or report of the developer's actions. Deliver a credible, polished, coherent experience regardless of industry, technology stack, target audience, business model, or visual aesthetic.

**This skill is framework-agnostic and website-type-agnostic.** Apply to marketing sites, online stores, booking platforms, SaaS products, admin panels, marketplaces, portfolios, education sites, nonprofits, internal tools, landing pages, and anything else rendered as a website.

## Highest-priority boundary: developer work is not customer content

Developer instructions, tool results, build provenance, AI/agent activity, migrations, imports, design references, release notes, implementation notes, and completion reports must **not** become visible page copy by default.

Examples of text to **never add as customer-facing content merely because work was completed**:
- “Fully imported from [website].”
- “Successfully cloned/recreated from [website].”
- “Built with AI / generated by an AI agent.”
- “Background removed with hosted AI.”
- “Integrated with [API/SDK/provider].”
- “Component now responsive on mobile.”
- “This section was generated from the prompt.”
- “Database connected successfully.”
- “Your website is now production-ready.”

**Default decision:** remove implementation commentary rather than cosmetically rewriting it. Only show a message when it helps a real user understand the product, finish a task, make an informed decision, or recover from an issue.

## Non-negotiable product copy rules

1. **Write for the end user.** Speak in language appropriate to the site's actual customers, their goals, and brand. Use short, natural, specific, useful copy.
2. **Never leak prompts or implementation.** Do not display “as requested,” “according to your prompt,” “copied from,” “imported from,” “generated with,” “powered by [technology],” “hosted AI,” “API call successful,” or developer/agent status commentary unless the product intentionally sells this information as a documented feature or needs it for transparency.
3. **No generic AI marketing filler.** Avoid unearned phrases such as “revolutionize your journey,” “unlock limitless potential,” “elevate your experience,” “seamless solutions,” and repetitive grandiose claims. Prefer concrete customer benefits supported by facts.
4. **No content invented to fill a layout.** No fictional client lists, testimonials, statistics, awards, badges, pricing, trust seals, certifications, guarantees, integrations, staff bios, locations, timelines, product features, inventory, or policies. If material facts are missing, keep sections concise, use clearly marked dev-only placeholders, or request required information from the developer—not the customer in the rendered page.
5. **Do not narrate a workflow unnecessarily.** Display status feedback only when it is genuinely useful. Show “Removing background…” while waiting, “Background removed” after success if confirmation is helpful, and useful next actions when appropriate. Do not expose internal providers, models, servers, queues, or processing details by default.
6. **Separate customer UI from developer reporting.** Tell the developer what changed in the agent's chat/report or logs, not in product headers, feature cards, banners, toasts, modals, onboarding screens, or footers.
7. **Respect explicit product requirements and truth.** If users legitimately need provenance, licensing/attribution, AI-use disclosure, data handling, regulatory notices, security explanations, source credits, or accessible status messaging, provide accurate and appropriately placed content. Never remove required transparency in the name of avoiding “AI slop.”
8. **Do not copy another business's site identity.** References and imported assets may inform implementation where authorized, but don't publish third-party brand names, protected text, logos, claims, testimonials, or copyrighted materials as the client's own. Preserve required licenses/attributions and ask for clarification if rights are uncertain.
9. **No false progress or unsupported success.** Confirm backend/application state before claiming work succeeded. Provide helpful, truthful error handling; keep raw exception details in developer logs only.
10. **Avoid unnecessary UI elements.** Do not add “New,” “AI-powered,” “100%,” “Premium,” status chips, badges, unnecessary cards, explanatory tooltips, or decorative copy without a meaningful audience purpose.

## Adaptation protocol (before designing or editing)

Infer from project content and requirements when available:
- Audience and primary user jobs.
- Site type and product stage (landing page vs. dashboard vs. checkout vs. admin tool).
- Brand voice, terminology, visual identity, language, locale, and accessibility needs.
- Constraints imposed by current design system and components.
- Which visible status messages, disclosures, and technical details are legitimately useful to this specific audience.

**Never impose one generic tone or aesthetic on every website.** For a hospital site be calm and precise; for a fashion store reflect its established brand; for a developer dashboard technical labels may be essential. If there is insufficient brand context, choose clear neutral professional copy rather than inventing a brand personality.

## Standard work sequence

### A. Scope and inspect

1. Read the user's request and repository conventions, copy guidelines, existing style system, and relevant code.
2. Find all newly affected rendered text: page headings, hero copy, tabs, CTAs, button labels, empty states, tooltips, toasts, loading/success/error states, dialogs, FAQ, meta titles and descriptions, alt text, placeholders, checkout, emails if part of the web workflow, and mobile layouts.
3. Identify questionable strings introduced by the current task or already present in touched surfaces. Do not indiscriminately rewrite unrelated brand copy.

### B. Implement

1. Build the actual requested feature; do not replace functional work with attractive placeholder UI.
2. Write essential UI copy from the user's perspective using accurate, task-oriented language.
3. Eliminate build/migration/import announcements, developer descriptions, and generic AI filler from rendered output.
4. Keep developer-only diagnostics in logs, comments where appropriate, tests, and the final developer-facing report.
5. Follow existing design patterns for typography, layout, spacing, interaction, responsiveness, loading feedback, error recovery, accessibility, and localization.
6. Do not add unrelated sections, features, brands, claims, animations, cards, or badges merely because they are easy to generate.

### C. Audit and verify

1. Inspect actual rendered page states and data paths, including success, loading, error, no-data, disabled, and mobile states relevant to the change.
2. Search touched code for suspicious marketing clichés, imported-site names, tooling/provenance announcements, raw technical errors, hardcoded lorem ipsum, and stale placeholders. A suspicious phrase is a review candidate, not an automatic deletion.
3. Ensure success and failure text reflects the real result. Do not claim a production deployment, integration, payment, or API result you didn't test.
4. Check navigation, keyboard accessibility, readable contrast, form labels, focus behavior, responsiveness, semantics, and any required privacy/legal disclosures.
5. Run relevant existing checks (lint, tests, typecheck, build, browser checks) when available; state what was actually checked.
6. Report code changes, warnings, and missing inputs **only in the developer conversation**, not on the website.

## Copy decision test

Before adding *any visible string*, ask:

1. Who is the intended reader? Is it a real product user rather than the developer?
2. Does it help them understand, decide, act, confirm, or recover?
3. Is it accurate, specific, natural, and consistent with this brand and context?
4. Does it reveal build process, original reference website, AI tooling, or backend internals unnecessarily?
5. Could it be removed with no loss of customer value?

**If (4) is yes or (5) is yes, remove it by default.** Exceptions: required or user-requested transparency, attribution, legally mandated disclosure, and genuinely technical user experiences.

## Examples: preferred behavior

| Agent-generated or awkward UI text | Better product behavior |
|---|---|
| “Fully imported from ExampleSite.com” | No visible message; report import to developer. |
| “Successfully recreated the original homepage” | No visible message. |
| “Background removed using cloud-hosted AI technology” | “Background removed” (only if confirmation is useful). |
| “AI-powered image processing in progress” | “Removing background…” |
| “We have successfully integrated Stripe payments” | Show a functional checkout, not a development status banner. |
| “Firebase authentication configured” | “Sign in” / “Create account” as applicable. |
| “API error 500 — model request failed” | “We couldn’t complete that. Please try again.” Include contextual next action. |
| “All product data synced from VendorXYZ” | No visible announcement unless data provenance is relevant or legally required. |
| “Explore our revolutionary cutting-edge solutions” | A specific, substantiated customer benefit or no heading at all. |

These are examples, not blanket string-replacement rules. Context matters.

## Non-goals and safeguards

- Do not conceal necessary information about AI, subscriptions, data transfers, payment providers, third-party content, accessibility, privacy, or legally mandated disclosures.
- Do not remove intentional technical content from docs, developer tools, API dashboards, admin logs, or technical product experiences just because it sounds technical.
- Do not delete real data or change business rules to improve how the interface reads.
- Do not redesign the site or remove meaningful content outside the task's authorized scope.
- Do not silently assert site completion, correctness, security, compliance, or performance without verifying.

## Project handoff

Your final message to the developer should briefly state:
- What you built or improved.
- What customer-visible text was removed or rewritten (if any).
- What testing was performed and the outcome.
- Any missing content, implementation concerns, or required approvals.

Do not insert that handoff information into the site's rendered UI.
